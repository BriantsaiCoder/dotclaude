# /sdd — 輕量規格驅動開發

核心規矩只有一條：**動手寫程式之前，先把要做什麼寫清楚。** 寫完讓使用者確認，同意了才開始寫；每做完一小步就回報；不要一次把所有東西做完。

## 何時用 /sdd（vs 升級重型流程）

`/sdd` 是**輕量**路徑，給「單檔 / 單一行為 / 1 天內可完成、不值得動用 superpowers 重鏈」的小需求。

- **適合 /sdd**：加一個小功能、修一個明確的 bug、一段小重構。
- **應升級到重型流程**（CLAUDE.md 的 `mp-grill-with-docs → brainstorming → writing-plans → executing-plans/subagent-driven`）：需求模糊需要拷問、跨多模組 / 架構性變更、需要 ADR / CONTEXT.md 領域決策、需要 TDD 紅綠循環內嵌的正式計畫。
- 判不準就**停下問使用者**走哪條，不要自己選。

## 開發紀律

- 一次只做一個需求；不要一個對話想把所有功能做完。
- 不要自己加沒被要求的功能，也不要過度設計（遵守 ponytail / Push back）。
- 沒把握的地方就問，不要用猜的。
- 動手前先看專案裡有沒有現成的東西可重用，不要重複造輪子。

---

本次階段由 `$ARGUMENTS` 的第一個詞決定（提案 / 實作 / 歸檔）。若沒給或無法判斷，先說明用法並停下。短名稱規則：英文、小寫、連字號連接（例 `add-todo`、`fix-login`）。

## 階段一：提案

當輸入是「提案」並描述一個需求時：

1. 幫這個需求取一個英文短名稱。
2. 判斷類型：新功能 / 修 bug / 重構（三選一）。
3. 在目前工作目錄下建立 `sdd/<短名稱>/proposal.md`，內容含：
   - `## 為什麼做`：這個需求想解決什麼問題
   - `## 要改什麼`：會新增或改動哪些行為（條列）
   - `## 影響範圍`：大概會碰到哪些檔案（新增的、要改的）
4. 建立 `sdd/<短名稱>/tasks.md`，把工作拆成可打勾的小步驟，每條前面 `- [ ]`：
   - 每條小到 1 小時內可做完。
   - 整份不超過 10 條；超過代表需求太大，**提醒使用者先拆小**。
5. 在 `tasks.md` 最後加 `## 驗收條件`，用白話「情境」描述「做完後應該長怎樣」，例：
   - 情境：當使用者點擊「新增」按鈕，就把輸入框的文字加到清單最下面
   - 情境：當輸入框是空的就按新增，就不新增，並提示「請先輸入內容」

寫完這兩個檔後，把重點貼給使用者看，然後**停下來等確認**。除非使用者說「實作」，否則不要寫任何程式。

## 階段二：實作

當輸入是「實作」時：

1. 先讀 `sdd/<短名稱>/proposal.md` 和 `tasks.md`，搞清楚要做什麼。
2. 從上到下，一次只做一條 `- [ ]` 任務。做之前先看有沒有現成的東西可重用。
3. 做完一條、打勾之前，回頭再讀那條任務和「驗收條件」，確認真的做到、沒漏。確認 OK 才把該條 `- [ ]` 改成 `- [x]`，並再看一眼 `tasks.md` 確認那行真的變了。
4. 每完成一條就簡短回報「第幾條完成」，再做下一條。
5. 做到一半發現規格漏了東西或方向不對，**停下來告訴使用者**，等決定，不要自己亂改規格、也不要硬幹。
6. 全部打勾後，告訴使用者「全部完成」並請驗收。

## 階段三：歸檔

當使用者驗收沒問題、說「歸檔」時：

1. 打開 `sdd/<短名稱>/tasks.md`，確認每條都是 `- [x]`。還有沒打勾的，先告訴使用者，不要直接歸檔。
2. 都完成後，用 `date +%F` 取今天日期（格式 YYYY-MM-DD），把整個 `sdd/<短名稱>/` 資料夾移動到 `sdd/archive/<今天日期>-<短名稱>/`（用 `git mv` 若在 git repo）。
3. 回報歸檔完成，並用一句話總結這次做了什麼，方便日後回查。
